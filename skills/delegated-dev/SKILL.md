# 委派开发

## 分工与覆盖

由当前主会话模型统筹、制定计划和最终验收。首次使用时通过可点击菜单选择实现者和审核者：实现者优先推荐可用的 DeepSeek，审核者默认推荐当前主模型。推荐不等于已经选定。主模型不绑定任何品牌，不要求用户切换主会话，也不声称已经切换。

按以下顺序解析角色：本次用户明确指定 > 本会话用户已明确设定且仍适用的分工 > 上述默认。临时覆盖不修改此 Skill，不自动持久化到其他会话。

用户可以指定实现者、计划者、独立审核者及具体模型、提供方和推理强度。指定额外计划者或审核者时，把对应任务委派出去，当前主模型仍负责协调及最终汇报。未指定额外审核者时由主模型审核，不无故增加代理。

开始前用一句话说明本次分工。明确且可用的配置不必反复确认。

## 首次选择与会话内复用

1. 首次实际开发且本会话没有已确认的分工时，先检查可用工具，再用 ask_user_question 提供可点击选项。不要要求用户记住或输入模型 ID，也不要把示例品牌当作真实候选。
2. 先询问“用哪种方式写代码？”：DSH 子智能体（云端/已接入的本地模型）、远程 CLI；只提供当前工具支持的方式。审核方式可同时询问：当前主模型（推荐）、DSH 独立审核、远程 CLI 独立审核。用户已明确的角色或方式直接跳过，不重复问。
3. 按所选方式进入下文对应发现流程，再列出真实模型的友好名称及提供方。DSH 路径内可用的 DeepSeek 优先推荐，不默认切换到远程 CLI。内部维护选项到执行配置的映射：DSH 为 provider/model；远程 CLI 为 host/绝对 cwd/CLI provider/model，以及用户明确选择的 mode/thinking/speed。同名模型用提供方和执行方式区分。候选很多时分级选择或提供“更多模型”；没有交互工具时用编号列表。
4. 用户选定后，用一句话确认分工，在本会话沿用。保存的是对话内角色与模型的对应关系，不修改全局设置、Skill 或跨会话记忆；“当前主模型”随当前会话模型变化，不固定为某个旧型号。
5. 用户说“换个模型”“重新选分工”时重新查询并打开菜单；指明“换写代码的模型”或“换审核模型”时只更换对应角色。单次覆盖仅影响本次任务，不覆盖原有会话选择；明确要求以后沿用时才更新会话选择。
6. 已确认模型后续不可用时解释原因，重新列出实际候选让用户选，不静默降级。会话恢复后若仍能明确读取原选择则复用；无法恢复对应关系时重新询问，不假装记得。
7. 用户仅要求计划、讨论 Skill 或修改 Skill 时，不弹出开发模型选择菜单，也不启动实现代理。

## 两种执行方式

### A. DSH 子智能体（包括本地模型）

通过 list_subagent_models 先查询提供方，再查询其模型；使用 subagent 并显式传入选定的 provider/model。用 send_message 继续同一子智能体，用 interrupt_agent 停止不再需要的工作，遵守通知机制，不忙轮询。

本地模型沿用相同路径，不因为模型运行在本机或局域网就假设它拥有项目文件。本地模型须已接入 DSH 提供方，且实际调用能执行所需工具。列表缺失时说明尚未发现该模型，不自动安装服务、更改 API 地址或授权；列出其他选择或请用户先完成接入。工具调用失败时报告限制，不伪装已完成代码修改。

### B. 远程 CLI 插件

1. 调用 remote_agent_list 发现已保存主机、近期项目和代理。用友好名称列出主机与项目候选。当前任务已有已验证的远程 host 和绝对项目路径时优先复用，并简短说明；否则让用户点选。近期项目只是候选，不代表就是当前任务。缺少项目路径时询问用户，不猜测本地锚点对应的远程路径。
2. 在选定 host 与绝对 cwd 上调用 remote_agent_providers，查询实际安装、登录状态、CLI provider、模型及支持的权限模式、思考强度和速度。需要时刷新发现结果。只展示实际返回的候选；不可用或未登录时告知用户，不能自动安装 CLI 或操作凭据。
3. 让用户选择 CLI 和模型，不要求记 ID。若 CLI 只支持默认模型或没有返回模型目录，允许明确标注“CLI 默认模型（具体型号未确认）”，调用时省略 model；不要声称精确锁定了某型号，也不要借用 DSH 模型目录填充远端 CLI 菜单。DSH provider 与 CLI provider 是不同命名空间。
4. 默认沿用远端权限与思考/速度设置，不选择跳过权限确认的模式，不为提速自动提高费用档位。若用户指定参数，先核对该 CLI 的发现结果。远端权限独立于 DSH 子智能体授权；主会话的授权或模型白名单不会自动传递过去。
5. 用 remote_agent_create 在确认的 host/cwd 创建代理。prompt 必须自包含：角色、需求、项目路径、适用指令、允许修改范围、计划、验收标准、测试与回报要求。远端 CLI 看不到当前对话，也不应依赖本机 Skill 路径。明确禁止递归委派和未经授权的提交、推送、部署。
6. 记录返回的 agentId 和执行配置。需要继续独立工作时用 wait=false；需要结果时用 remote_agent_wait，不忙轮询、不重复启动同一任务。代理空闲后用 remote_agent_send 交付修复意见；运行中要改变任务先明确停止或中断，不能误以为发送成功。用户取消时用 remote_agent_stop 停止对应工作。
7. 新任务默认新建代理；只复用本任务已确认、角色和目标一致的代理，不擅自接管列表中无关代理。改主机、目录、CLI 或模型时新建匹配代理，不假设 send 能切换执行配置。
8. 远程独立审核使用单独代理，提示其只读审核，并在发现结果支持时选择合适的只读权限模式。若只有提示词约束，明确这不是权限隔离；用户要求严格只读而工具不支持时应停止并说明。实施与审核同一工作区时先等实施停止写入，再审核实际改动。

### 跨执行方式的项目一致性

- DSH 本地模型、远程 CLI、当前主模型可以混合分工，但必须能访问同一份待审改动。记录 host、绝对项目路径、分支/HEAD 和已有未提交修改；不要把同名目录或相同仓库地址视为同一工作树。
- 优先让远程实现和审核指向同一已确认工作区。主模型通过当前已验证的 remote_workspace 读取 diff/代码和测试证据；该工具不等于可以访问任意远程主机。
- 若执行主机不同且没有共享工作区，先说明代码传递问题，取得用户同意再制定明确的 patch/同步方式；不要隐式复制整个仓库、凭据或覆盖未提交修改。
- 主模型无法直接读取目标时，可在同一目标创建只读审核代理获取真实 diff、相关代码与测试证据，并注明验证来源；只有实现者完成摘要不算独立审核。无法取得足够证据时标注验证受限，不称验收通过。
- 同一工作树避免多个写入者；跨主机、执行方式或模型切换不改变原有修改权限与验收标准。

## 模型与环境预检

以下模型发现与 provider/model 显式选型规则针对 DSH 路径；远程 CLI 使用上面的独立发现和调用规则。

- 使用当前工具提供的模型发现能力（如 list_subagent_models）查询提供方、精确模型 ID 和支持的推理强度，不猜测 ID 或仅凭显示名调用。菜单中的目录候选不代表已验证授权或调用成功，不作此保证。
- 若用户使用模糊名称且存在多个匹配，用上述选择菜单让用户点选，不要求其自行查 ID。
- 创建实现或审核子智能体时显式传入确认的 provider 和 model；仅使用工具支持的参数。需要另选模型时，不依赖不能显式选型的委派方式。
- 指定模型不可用、未授权、额度耗尽或委派失败时，报告原因并询问用户如何继续；不要静默换模型，也不要自行接管实现。目录可见不等于调用一定成功。
- Skill 不能授权模型或绕过工具权限。若工具不支持所需分工，说明限制。
- 确认项目真实位置及适用的项目指令。远程工作区不是本机锚点目录；让子智能体使用正确主机、工作区和访问工具。无法确认子智能体可访问目标时，先解决访问问题，不让它在本机锚点写代码。

## 执行步骤

### 1. 计划

读取需求和必要代码，保留用户未提交的修改。制定与任务规模相称的实现步骤、修改边界、验收标准和测试方案。用户只要求计划时，到计划为止，不启动代码实现。存在产品决策或破坏性操作时先澄清。

### 2. 委派实现

给实现者自包含的任务说明：目标、工作区、相关路径、已知上下文、计划、允许改动范围、不能改动的内容、验收标准及测试命令。要求它直接完成授权范围内的实现，并返回修改文件、关键设计、实际运行的测试及结果、未解决问题。

明确告诉实现子智能体：它只是实现者，不应再次套用本 Skill 发起递归委派；读取项目指令并遵守权限，不自行提交、推送、部署或清理用户修改。

默认串行执行；只有任务写入范围独立时才并行。避免多个代理同时修改同一文件。遵守运行时递归深度和并发限制；常规流程只需主模型直接调度一层子智能体。

主模型在实现期间可以调查、规划测试和准备审核，不重复编写同一实现。跟踪代理 ID，并按工具约定等待和收集结果。

### 3. 审核

由主模型或用户指定的独立审核者读取实际 diff、必要的完整代码及测试输出，核对需求、正确性、回归风险和安全边界。不能仅凭实现者的完成报告判定通过。

独立审核子智能体只审核，不修改代码；返回具体文件位置、问题、影响及建议。主模型汇总审核结果，并实际执行或核验合适的验证。测试没有运行、环境受限或验证不完整时，明确说明，不能说成通过。

### 4. 修复与复审

将审核问题和复现方式交回实现者修复，再审核最新改动并验证受影响行为。优先复用同一实现子智能体及其已确认的模型；用户要求改变角色模型时，为新角色创建匹配的新代理，不假设旧代理已换模型。

默认最多进行 3 轮修复复审；用户另有要求时以用户为准。仍未通过则汇报剩余问题并询问是否继续，不无限循环，不隐瞒风险。

### 5. 验收与交付

总结实际角色及模型、主要改动、审核结论、测试结果和剩余风险。区分“实现完成”“审核通过”和“验证受限”。不把未经验证的结果称为已验收，不自动提交、推送或部署。

## 使用示例

- “协作开发，实现登录功能。”：首次选择执行方式，再按需选择模型、远程主机和项目；本会话后续沿用。
- “协作开发，用本地模型写代码。”：查询 DSH 已接入的实际模型，点选本地提供方和型号，不自行部署模型。
- “协作开发，用远程 CLI 写代码，你审核。”：发现主机和项目，查询远端 CLI 与模型，确认后启动；当前主模型核验同一工作区的实际改动。
- “这次换成远程 CLI 审核。”：只为审核角色选择远端配置，确认它能访问待审改动后再启动只读审核。
- “换个写代码的模型。”：刷新实际候选，只重新选择实现者，无需记住型号或 ID。
- “使用 delegated-dev，这次让 Qwen 写代码。”：当前主模型计划和审核，本次实现者覆盖为 Qwen。
- “使用 delegated-dev，DeepSeek 写代码，再让 Astra 独立审核。”：当前主模型统筹，DeepSeek 实现，Astra 子智能体只读审核。
- “使用 delegated-dev，只给计划，先不改代码。”：仅提供计划，不启动实现代理。

本 Skill 是可复用的协作指令，不是权限隔离或强制流程引擎。
