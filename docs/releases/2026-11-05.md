## 已读状态在设备之间同步

| 插件 | 市场旧版 → 本次版本 | 内容 |

| Remote Agents | 0.2.100 → **0.2.101** | 用户反馈手机上“已完成”的 5 条，在 MacBook Air 上都点过了。手机的已读只存在手机本地，DSH 的未读只在每个页面的内存里，设备之间没有任何同步。现在共享登记里每个会话多一个 `read.json`，记录历史读到哪一条，只增不减，读到末尾就算已读。DSH 页面上报屏幕上的对话，条件是窗口可见且有焦点，这样开着 Air 离开时跑完的回合，手机上仍显示“已完成”。别处读过之后，页面约 5 秒内清掉“已完成”。 |
| Mobile | 0.3.5 → **0.3.6** | hub 把别处的已读换算成本机的位置（`readSeq`）发给手机，手机打开会话时也会上报。要和 Remote Agents 0.2.101 一起更新。 |

一次已读只算到它发生时会话显示的内容。DSH 模型的回合不写共享历史，旧的已读在位置上仍然覆盖它，所以 hub 对每个已读标记只应用一次，页面则记下回合开始时的标记来比较。如果改成“未读出现时才比较”，手机发起的回合约有一半会在 Air 上留下假的未读，因为手机的已读可能比 Air 跟随结束更早到。

验证：新增 Remote Agents 6 项、Mobile 6 项测试，两个 DSH 实例之间的同步用的是真实的注册表脚本。Remote Agents 全量 571 项中通过 547 项、失败 3 项、取消 20 项，失败和取消的项目与干净的 main（875f055）完全相同；Mobile 全量 33 项全部通过。在隔离的 DSH 0.2.1-rc.5 网页版（无头 Chromium，没有配置机器，已读标记由脚本模拟）实测：回合在别的对话背后跑完显示 Completed，没人读时一直保留，标记出现后约 4 秒清除，回合开始前就有的旧标记不会清除，新标记约 2 秒清除；打开对话会上报，页面没有报错。真实数据中 66 个共享会话只有 5 个在最后一个回合结束后还有记录（进行中的回合、错误、中断），所以和历史末尾比较是安全的。

**未验证：** 真实的 Air 加真实手机的完整链路；桌面版；窗口失去焦点只有单元测试。已知限制：升级前点过的对话要再打开一次标记才会消失，那些点击没有记录；每个 DSH 都要升级，它的已读才算数；只覆盖共享的 CLI 对话，手机的“后台任务”列表不参与；已读如果赶在 hub 开始跟随这一轮之前到达，手机上这一轮仍可能显示“已完成”，打开一次即可；依赖 DSH 内部结构（`uiSession` 的 `completionUnread` 和 `publishStatus`），不存在时只是不清除。Mac mini 上的手机端 DSH 和手机 PWA 没有更新。

## 关掉 DSH 也不断：远程终端和 TUI 常驻远程机器

| 插件 | 市场旧版 → 本次版本 | 内容 |
| --- | --- | --- |
| Remote Agents | 0.2.95 → **0.2.96** | 用户反馈 TUI 和自己开的远程终端都很卡、会断线，希望关掉本机 DSH 再打开都保持住。以前 CLI 和 shell 跑在 DSH 启动的 `ssh` 下面，这条连接一断就跟着结束，正在跑的一轮也丢了。现在它们跑在远程机器的常驻进程里，DSH 只是连上去看：断线自动重连，电脑休眠唤醒后立刻重连；重开 DSH 后 TUI 接回同一个进程，侧栏的终端标签也会自己回来；屏幕和滚动记录由常驻进程里的无头 xterm 保留。没有用 tmux：它会接管滚轮和选字，还会吞掉 Codex 的状态信号；常驻进程把 CLI 的字节原样转发。Node 开不了 PTY，macOS 的 `script` 又拒绝非终端的 stdin，所以用几行 Python 持有 PTY。关闭标签、`exit`、归档 TUI 才结束；没人回来的 7 天后结束。远程机器没有 Python 3 或 Node.js 22 时退回普通连接，并在终端里提示。同时关掉这些连接上 OpenSSH 的按键节奏保护（`ObscureKeystrokeTiming`）：回环上每个按键 327 字节对 36 字节，回显 p95 27.6 ms 对 1.6 ms；代价是网络上的观察者能从包的时间看出打字节奏，和 OpenSSH 9.5 之前一样。 |

卡顿的实测：从 Mac mini 到用户的 MacBook 丢包 2.3%、往返最高约 100 ms，同一时刻到另外两台机器都是 0% 丢包。80 次探测里 77 次走 peer-relay（中位 32 ms），2 次直连（20 ms），1 次回退到洛杉矶的 DERP（1.45 秒）。丢包是插件解决不了的，这次只是减少了它的影响，所以不能说已经不卡。桌面版自身的渲染有没有拖慢也没有测。此前“滚动不走网络”的判断是错的：Claude Code 的滚动是它自己绘制的，滚轮也要走一个来回。

验证：Remote Agents 新增 24 项测试；全量 547 项中通过 526 项、失败 1 项、取消 19 项，和之前干净的 main（be96e20）对比没有新增失败，都是已有的 relay 测试问题。在隔离的 DSH 0.2.1-rc.5 网页版（无头 Chromium，SSH 到本机）用这个最终构建实测通过：真实的 Claude Code（Haiku）回复写到 40 时停掉 DSH，回来时已写到 2007，还是同一个进程，之后写完；侧栏终端经过刷新、重启、杀掉 ssh、调整大小和关闭标签；归档只结束自己的常驻进程。rebase 之前的构建上还测过：真实的 Codex（GPT-6-Luna）在重启后写完并继续对话，重启后团队工具仍能调用，`/exit` 后留在同一个常驻进程，`exit 3` 显示退出码，新建终端恢复对话。真实的 Linux 主机上手动验证了接回和退出。回显没有变慢（回环 p50 7.0 ms 对 7.9 ms），空闲时常驻进程约占 27 MB 内存，CPU 为 0。

实测中修掉的问题：`tuiEnd` 漏加进接口白名单，归档时常驻进程不结束；Python 自己忽略 SIGPIPE，这个设置会带进 shell，让管道报错而不是结束；没人连着时 CLI 问终端（比如光标位置）得不到回答，Codex 会超时，改由常驻进程代答；序列化不恢复隐藏光标和 SGR 鼠标模式，Claude Code 重连后光标位置不对、滚轮失效，改由常驻进程自己记录；不再读取的客户端不能卡住 CLI，5 秒后断开它，下次连接拿到完整屏幕。

**未验证：** 桌面版；Windows 客户端。已知限制：`docker` 这台机器的 PATH 上没有 Node，只能用普通连接；DSH 重启后左侧这一行要点开才知道状态，CLI 其实一直在跑；已经开着的终端要到下次打开才生效；依赖 DSH 内部结构（`terminalController.spawn`/`close`、`webTerminals.view`），DSH 升级后可能要跟着改，改了会退回以前的行为。Mac mini 上的手机端 DSH 没有更新。
