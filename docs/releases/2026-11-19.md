## 手机 Web App (PWA) 0.1.0 — 安装到手机主屏的 DSH 底栏变成深色

用户把 DSH 网页版装到 Android 手机主屏后说「底下是白色的」：顶部状态栏会随深色主题变黑，最底下的系统导航栏（弹出/切换键盘时最下面那条也是）却是白的。DSH 页面加载后会按页面底色写 `<meta name="theme-color">`，但已安装的应用的底栏和窗口底色取自应用清单，而 DSH 从 0.2.2-rc.1 起在 `manifest.webmanifest` 里把 `theme_color` 和 `background_color` 都写成了 `#ffffff`。插件初稿由另一个模型写成，审核后改了下面几处再发布。

| 插件 | 市场旧版 → 本次版本 | 内容 |
| --- | --- | --- |
| 手机 Web App (PWA)（`dsh-pwa`，新插件） | — → **0.1.0** | **用 DSH 自己的清单，只换两个颜色：**在 `webServer` 上注册精确路由 `/manifest.webmanifest`（`resource` 形式，GET/HEAD/405 由 DSH 处理），读取正在运行的 DSH 的 `manifest.webmanifest`（先从 `frontend-static` fiber 配置的 `distIndex` 找，再从 `process.argv[1]` 解析 `@deepseek-ai/dsh-web-frontend`），其它字段原样保留，`theme_color`、`background_color` 换成 `#151517`（可配置）；按 mtime/size 重新读取，DSH 升级改了清单会自动跟上。**插件自己不带清单：**初稿内置的回退清单是 0.2.1-rc.5 那份（`display: fullscreen`、只有 `favicon.svg`），找不到 DSH 文件时会把已安装的应用改成全屏、换图标，现已删除；读到 DSH 的文件之前不注册路由（`frontend-static` 晚启动时在 `internal/status` 上重试），读到之后文件消失或无法解析就继续用上一次的内容。**不改页面：**初稿往 `<head>` 注入的 html 底色样式已删除，它和 DSH 自己的启动主题行（首屏前把 body 涂成 `#151517`，非 macOS 下 body 底色铺满画布）重复。README 里「DSH 清单没写颜色」的说法改正为写的是白色。 |

源码与版本提交：`c9aa523`；市场包：`c26ba3ecc44ed64aa7ab8185a69721042512967e`；市场索引：`594a067`。

### 验证

- 类型检查、8 项测试、构建通过；市场包 `lib` 与本地测过的构建逐字节相同。测试覆盖：保留 rc.3 清单的全部字段只换颜色、304、跟随上游修改、文件损坏或删除时保留上一次的内容（每种问题只警告一次）、从没读到时不提供任何清单、`frontend-static` 晚于插件启动时之后再接管（去掉重试后这项测试失败）、卸载后交还路由。
- 用 Mac mini 上 DSH 0.2.2-rc.3 自己的 cordis 4.1.0、`dsh-host-webserver` 和 `dsh-host-frontend-static`（按 `dsh-web-app` 的方式挂载）跑插件：两种启动顺序下 `/manifest.webmanifest` 都返回 rc.3 原清单（standalone、3 个 PNG 图标）且颜色为 `#151517`，304/HEAD/POST 405 正常，页面里没有新增 `<style>`；指定一个不存在的清单路径时不接管路由，返回 DSH 的白色清单并记一条警告；卸载后回到 `#ffffff`。

### 兼容

dsh.lalaze.com 的 Caddy 目前自己回答 `/manifest.webmanifest`（2026-11-19 放的深色副本），所以在 hub 上装这个插件不会改变手机经公网拿到的清单；要用插件的版本，需要撤掉 Caddy 的 `handle @manifest`，把这个路径放回转发列表。已安装的应用要卸载重装，或等 Chrome 定期检查清单后才会更新。浅色主题下底栏也是深色（清单只能写一个颜色）。

## 远程终端 0.1.21 — 新开的 TUI 顶上不再出现 `^[[I^[[O`

用户新开一个 Claude Code TUI，看到 Claude 的标志前面多了 `^[[I^[[O`（截图）。这是 0.1.20 带来的问题：页面不管 CLI 有没有开启焦点报告都会认领画面，TUI 出现在眼前 300 ms 后发 ESC[I + ESC[O。新开的 TUI 这时还在启动，DSH 的 PTY 仍是普通的回显模式，要等 attach 客户端连上 holder 后执行 `stty raw -echo` 才关掉回显，认领就被内核原样回显成 `^[[I^[[O`。实测：在独立的 PTY 里像 DSH 那样运行 hub 上装的 `Remote Claude` 启动器（新 holder），回显一直持续到 0.616 s，0.303 s 发出的认领被回显，紧接着就是 Claude 的输出，与截图一致。CLI 没有收到这些字节：attach 客户端在 CLI 没开焦点报告时把它们丢掉了。0.1.19 及以前不会这样，因为那时页面只在 CLI 开启焦点报告后才认领，而那时终端已经是 raw 模式。

| 插件 | 市场旧版 → 本次版本 | 内容 |
| --- | --- | --- |
| 远程终端 | 0.1.20 → **0.1.21** | **主机在终端里画出内容之前，页面不认领画面：**`claimScreen` 新增 `drawn`，光标还在原点且没有滚动过（新终端的状态）时什么都不发；拿不到光标位置的 xterm 视为已画出，保持原行为。DSH 只把 PTY 的输出写进这个 xterm（`dsh-client-ui-sidebar-terminal` 的 `render.frame`），所以光标没动就表示启动器还没输出任何东西。不会漏掉认领：客户端加入 holder 时会按它的 hello 取得画面大小。 |

源码与版本提交：`5b77773`；市场包：`464b27b58265f4ad972d794dbff0cafb7ac47f57`；市场索引：`553c88e`。不需要重启；每台设备刷新页面后生效。

## 远程终端 0.1.20 — Antigravity 的 TUI 会跟随你正在看的设备改变大小

用户在电脑上打开一个在手机上用过的 Antigravity TUI 对话（「Mobile Web App Keyboard Color」），说「tui 样式不对」：窗口中间只显示窄窄一列，内容按大约 41 列折行。实测这个对话的 holder 有两个客户端，都来自 hub 的 DSH：电脑页面 120×54，手机页面 41×43，agy 的 PTY 是 41×43，也就是画面还在手机手里。0.1.10 起画面靠焦点报告（ESC[I）跟随你转向的设备，但页面只在 CLI 开启了焦点报告（`?1004h`）时才发；Claude Code 和 Codex 会开启，Antigravity 1.5.12 从不开启，所以只有在电脑上打字才能把画面要回来。

| 插件 | 市场旧版 → 本次版本 | 内容 |
| --- | --- | --- |
| 远程终端 | 0.1.19 → **0.1.20** | **页面不管 CLI 是否开启焦点报告都认领画面：**`claimScreen` 只在「终端有焦点且 CLI 开启了焦点报告」（xterm 自己已经报告过）时不发，其余情况都发 ESC[I + ESC[O；`useScreenClaim` 另外在终端获得焦点（host 上的 `focusin`）时认领，因为 xterm 不会替没开焦点报告的 CLI 报告。**连接进程不把焦点报告转给没要的 CLI：**`holder-protocol.ts` 新增 `FocusReports`（从输出里跟踪 `?1004h/l` 和 RIS，保留 32 字符尾巴应对被拆开的序列；加入时 holder 的快照以 RIS 开头、带着 `?1004h`）和 `onlyFocusReports`；attach 客户端在 CLI 没开启时丢弃只含焦点报告的输入。认领规则（`screenClaim`、`FOCUS_SETTLE_MS`）和 holder 守护进程都没变。 |

源码与版本提交：`6024248`；市场包：`7e3a241474c8e74195d34594c41c288f6012ed2c`；市场索引：`3ff4a26`。不需要重启；每台设备刷新页面后生效。
