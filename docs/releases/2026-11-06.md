# 插件发布记录 — 2026-11-06

## TUI 里选中的文字能复制了

| 插件 | 市场旧版 → 本次版本 | 内容 |
| --- | --- | --- |
| Remote Agents | 0.2.108 → **0.2.109** | 用户反馈 Claude Code 的 TUI 里选中文字后复制不出来。现在松开鼠标就已复制，不用再按 Cmd+C，中文和多行都可以。鼠标静止一会儿后直接按下拖选，也不会再只复制到开头几个字。 |

原因有两个，都在真实的 Claude Code 2.1.319 上测到：

- Claude Code 全屏运行（备用屏幕，鼠标模式 `any`），高亮是它自己画的，所以 xterm 里没有选区，Cmd+C 没东西可复制。经 SSH 时它只用 OSC 52 请求写剪贴板，而 DSH 的终端没有这个处理器。修复前可以看到请求带着完整文字到了 xterm，剪贴板没变。它提示的“按住 Shift”在 Mac 上也不管用，因为 DSH 没有打开 `macOptionClickForcesSelection`，这个提示本次没有处理。
- 安静一段时间后的第一个输入，会让 Claude Code 重发一遍 `?1000h ?1002h ?1003h`（测到停 8 秒会发，约 2.5 秒不发，准确阈值没测）。xterm 依次切到 VT200、DRAG、ANY，切到 VT200 时会摘掉拖动监听，要等下次按下才挂回。鼠标停在文字上不动、直接按下时，重发正好落在拖动途中，修复前只复制到 `DELT`。先移动鼠标再按下时，重发通常先到，没有问题。

做法：`src/client/workspace/tui-copy.ts` 通过 `findXterm` 拿到 TUI 的 xterm，注册 OSC 52 和 CSI 处理器。OSC 52 只写不读，`?` 查询不回答，只接受目标 `c` 或空，并且要求终端在视图内、页面有焦点，所以切走的 TUI 和另一个窗口不会改写剪贴板。优先用 `navigator.clipboard.writeText`，没有这个 API 或被拒绝时用 `execCommand('copy')`，文字由 copy 事件填入，焦点留在终端。按键按住且鼠标跟踪已开启时，忽略重复的 1000、1002、1003，其他模式照常。

验证：`pnpm check` 全仓通过，其中 Remote Agents 600 项，599 项通过、1 项跳过、没有失败。第一次运行时 `shared-sessions.test.ts` 的 `a message names the DSH that sent it…` 失败（断言时机），这个文件不引用本次改动的代码；这项单独跑 5 次都通过，整个文件跑 3 次有 1 次失败，所以是原本就不稳定的用例，没有处理，重跑全仓通过。发布后从市场安装 0.2.109（`d8e3157`），在隔离的网页版（无头 Chromium，`ssh://localhost`，真实 Claude Code，Haiku）上测试：

| DSH | 结果 |
| --- | --- |
| 0.2.2-rc.1 | 18 项检查全部通过，停鼠标后按下 3 种情况都拿到完整文字 |
| 0.2.1-rc.5 | 18 项检查全部通过，停鼠标后按下 3 种情况都拿到完整文字 |

18 项包括：真实回复后立刻拖选、中文、多行、之后按 Cmd+C 不会清掉剪贴板、之后打字正常、没有焦点的窗口不写、切走的终端不写、其他剪贴板目标被忽略、读取请求没有回应、重新加载页面不会重放旧内容、shell 里普通选区加 Cmd+C 正常、WebGL、没有剪贴板 API 时回退。Codex 0.166（`--no-alt-screen`）的鼠标模式是 `none`，走 xterm 自己的选区，只读了模式，没有在 Codex 里实际拖选。

**未验证：** 桌面版和真实的系统剪贴板，无头 Chromium 用的是自己的剪贴板。如果桌面版拒绝写入，控制台会有 `[remote-agents] The browser refused to copy from the terminal`。

**已知限制：** 只覆盖 TUI 对话。在侧边栏终端里打开的 Remote Claude 有同样的两个问题。

Mac mini 没有更新：这个修复只作用于打开 DSH 页面的那一端，手机 PWA 不用它。

## root 账户上 Claude 能用“完全访问”启动了

| 插件 | 市场旧版 → 本次版本 | 内容 |
| --- | --- | --- |
| Remote Agents | 0.2.107 → **0.2.108** | 用户反馈以 root 连接的机器上，回合启动失败（`REMOTE_START_FAILED`，`--dangerously-skip-permissions cannot be used with root/sudo privileges for security reasons`）。选“完全访问”或“沿用远端 CLI 设置”时，插件现在会在 root 账户上设置 `IS_SANDBOX=1`，Claude 能正常启动。其他权限模式不设置，CLI 的检查照常生效。 |

原因：这个报错来自 Claude CLI。2.1.319 在权限模式是 `bypassPermissions` 且 uid 为 0 时直接退出，只有设了 `IS_SANDBOX=1` 或 `CLAUDE_CODE_BUBBLEWRAP` 才放行。插件的“完全访问”传的就是这个模式。root 的 `settings.json` 把 `defaultMode` 设成 `bypassPermissions` 时，不传参数也一样，所以“沿用远端 CLI 设置”、模型探测和 TUI 也会被拒。

做法：启动前在远端执行 `if [ "$(id -u)" = 0 ]; then export IS_SANDBOX=1; fi`，覆盖“完全访问”、“沿用远端 CLI 设置”、模型探测和额度查询。判断放在远端，因为任何账户名都可能是 uid 0。没有用 `sh -c … exec "$@"` 包一层：relay 把 `argv[0]` 记成 `meta.command`，socket 不通时靠它核对进程是不是自己的 CLI，包一层后这一步会悄悄失效。现在的做法把变量设在 relay 的启动命令前面，由 daemon 传给 CLI，CLI 的命令行不变，远端的 relay 脚本也不用升级。

这个变量让 Claude 能不经询问以 root 执行任何命令，等于替用户绕过了 CLI 的 root 保护。这是用户明确要求的，README 和更新日志都写明了。没有额外加确认步骤。

验证：从市场取 0.2.108（`7ff9d27`，索引 `1b5f9fa`），用包里的编译产物，加上真实的 relay 和真实的 Claude CLI 2.1.319 运行。这台 Mac 没有 root，所以把 CLI 进程的 uid 伪装成 0，再用假的 `id` 控制远端判断的结果，配置目录是隔离的，没有用到账号：

| 场景 | 远端判断 | 结果 |
| --- | --- | --- |
| 完全访问 | root | 通过检查，走到 `Not logged in` |
| 完全访问（对照） | 非 root | 回合报错，和用户截图的文字相同 |
| 沿用设置，默认模式为 bypass | root | 通过检查，走到 `Not logged in` |
| 沿用设置，默认模式为 bypass（对照） | 非 root | 模型探测就报同样的错 |
| Accept edits | root | 通过检查，走到 `Not logged in` |

Remote Agents 新增 4 项测试。在最终提交上单独跑整包：591 项，590 项通过、1 项跳过、没有失败。

**`pnpm check` 没有全部通过：** 跑了 3 次，每次都是 Remote Agents 有 1 项失败，其他 14 个包全部通过。失败的都是 `shared-sessions.test.ts` 里用 Codex 跑的两个 DSH 用例，这次没有改动它们涉及的代码：

| 用例 | 修复版 `pnpm check` | 基线（`3e818da`） |
| --- | --- | --- |
| `a session read in one DSH reads as read in another…`（`read here at once`） | 3 次里失败 2 次 | `pnpm check` 跑 1 次通过；加压交替运行时失败 5/40（修复版 1/40） |
| `a message names the DSH that sent it…`（`the first prompt…`） | 3 次里失败 1 次 | 没有复现；单独加压修复版和基线各 0/96 |

加压交替运行的负载约 30–60，多数运行碰到 60 秒的文件时限，所以只跑了文件里的一部分用例。第一个用例已确认基线也会失败。第二个只出现过一次，没有查明原因。

**未验证：** 真正的 root 机器和一轮真实对话，伪装环境停在 `Not logged in`。CLI 的放行条件只确认过 2.1.319。桌面版。

**已知限制：** root 账户的默认模式是 `bypassPermissions` 时，TUI 对话仍会报这个错，和手动运行 `claude` 一样。TUI 没有设这个变量，因为它会留在 Claude 退出后的 shell 里。`IS_SANDBOX=1` 还会影响 CLI 的会话注册清理、529 重试和组织策略强制沙盒的判断，所以只在需要的启动里设置。

## 输入框的模型名不再带机器名

| 插件 | 市场旧版 → 本次版本 | 内容 |
| --- | --- | --- |
| Remote Agents | 0.2.106 → **0.2.107** | 用户反馈更新后输入框里的模型名多了机器名（`Opus 5.5 · macmini`）。装了 WorkBuddy 这类也给模型加标签的插件时，DSH 自带的选择器现在也显示 `Opus 5.5`，悬停提示和菜单行仍保留机器名。 |

原因：`conversation.input.model.label` 是 single slot，优先级数值最低的才渲染。`dsh-connect-workbuddy` 注册在 -0.5，对别家的模型直接输出完整的 `model.name`，所以我们注册在 50 的 `ModelLabel` 不会运行。之前的 DOM 兜底只认 Codex 选择器的纯文本标签，碰到原生选择器的多层嵌套就跳过。修复前在 0.2.2-rc.1 上对照：原生选择器单独用时省略，加上 WorkBuddy 后带机器名，和用户的截图一致；Codex 3.2.6 加 WorkBuddy 时省略，因为它的选择器拿不到 `renderSlot`，输出的是纯文本。

做法：DOM 兜底现在也处理 `[aria-haspopup="menu"]` 触发器内 `[data-provider-id^="remote-cli"]` 下唯一的文本节点，不限层级，只改 React 已有的文本节点。原生触发器的 title 是 `<模型名> · <强度>`，所以校验放宽为等于或以 `<模型名> · ` 开头。没有调低我们的优先级：那样会盖掉 WorkBuddy 自己的徽章，而 single slot 没办法把渲染交给下一个注册者。

验证：`pnpm check` 全仓通过，其中 Remote Agents 587 项，586 项通过、1 项跳过、没有失败；第一次运行时 `browser-devtools` 的一项浏览器用例在高负载下超时（`timed out: $0 evaluation`），这个包没有改动，单独跑 3 次都是 32/32，重跑全仓通过。发布后从市场安装 0.2.107（`5fee5bb`）和 npm 最新的 WorkBuddy 5.19.1，在隔离的网页版（无头 Chromium，没有跑真实回合）上检查选模型、切换模型和强度、窗口重新聚焦、切到本地模型再切回、悬停提示、菜单行和控制台错误：

| 组合 | 结果 |
| --- | --- |
| 0.2.2-rc.1，原生选择器 + WorkBuddy | 16 项全部通过 |
| 0.2.2-rc.1，Codex 3.2.6 + WorkBuddy | 16 项全部通过 |
| 0.2.1-rc.5，原生选择器 + WorkBuddy | 14 项通过；另外 2 项失败，因为这个配置的菜单里没有本地模型可选，切到本地模型这一步在 rc.5 上没有测到 |

发布前的构建在 0.2.2-rc.1 上单独用原生选择器也通过了。

**未验证：** 桌面版。“更新后才出现”的原因也没有确认，推测是旧的 Codex 3.2.1 不能在 0.2.2-rc.1 上运行，选择器换回了原生的；没有看过桌面版的插件状态，也没有测修复前的 0.2.1-rc.5。

**已知限制：** 有 WorkBuddy 时，打开菜单后“模型”那一格和菜单行仍显示全名，菜单行的机器名也不是灰色。从代码看，页面刚加载、模型目录还没返回时，可能会闪一下全名，没有实测。
