# DSH Remote Terminals

**English** | [简体中文](README.zh-CN.md)

Terminals in a remote workspace that keep running when DSH closes, Claude Code and Codex as a conversation's own view, and new workspaces from a project's Git worktrees.

**Needs [Remote Agents](../remote-agents/README.md) 0.2.130 or newer**, installed in the same DSH. The machines, their SSH connections and the remote workspaces are saved there; this plugin works on them and keeps no machine list of its own. Without Remote Agents it loads and does nothing. Until 0.2.129 everything here was part of Remote Agents.

## Terminals

- **Terminal:** in a remote conversation, **New terminal** opens an interactive SSH terminal in the workspace, or choose **Remote workspace** in the native terminal's shell menu. The panel has no separate command runner. Terminals use the remote account's normal privileges. A missing or invalid binding fails explicitly.
- **Terminals outlive DSH:** the shell or CLI in a remote terminal keeps running on the remote machine when DSH closes, the computer sleeps or the connection drops. A lost connection reconnects by itself, and a sidebar terminal's tab comes back by itself after a restart, showing the same process with its screen and scrollback. Closing the tab, `exit` or archiving a TUI conversation ends it; one nobody returns to ends after 7 days, and a restart of the remote machine ends them all. This needs Python 3 and Node.js 22 on the remote machine; without them the terminal says so and uses a plain connection, which ends with the connection. These connections also turn off OpenSSH's keystroke-timing protection (`ObscureKeystrokeTiming`), so that typing is not held up on links that drop packets.
- **Claude or Codex directly in a terminal:** choose **Remote Claude** or **Remote Codex** in the native terminal's shell menu to start the interactive `claude` or `codex` in the same remote workspace; it leaves you in the remote shell when it exits. The session belongs to the remote CLI: it does not appear in a DSH conversation and does not get DSH's shared MCP servers and skills. Run `claude --resume` or `codex resume` in the remote directory to continue it. While you move between remote conversations, **New terminal** keeps opening it; leaving them gives back your own shell, and coming back returns to **Remote workspace**.

## TUI conversations

in a new conversation of a remote workspace, select a remote Claude or Codex model and click its icon at the bottom left of the composer (the Claude mascot or Codex's cloud logo; other models do not show one). The conversation's Chat tab becomes the interactive CLI, started with the model and effort you selected, and the composer is hidden. The terminal sits in a centered column over a translucent background that shows your wallpaper, and CJK text is scaled from the system font to fill its cells, so it does not read spaced out. Colors Claude Code draws itself, such as the message bar and input border, can be changed on the remote machine with `/theme` or `~/.claude/themes/`. It is drawn with WebGL, which shows what you type sooner than the page's own rendering; the button in its bottom-right corner switches that and the background blur, and a browser without WebGL keeps the page's rendering. Local scrolling, in the same menu, is on by default: Claude Code starts with its classic renderer, the conversation stays in the terminal's own scrollback (10,000 lines), and the wheel scrolls it there instead of asking the remote Claude Code to repaint the screen for every step, so scrolling stays smooth on a slow or lossy connection. In exchange Claude Code's fullscreen features, such as clicking to expand and jumping to the bottom, are not available; switching it off brings fullscreen back. The switch applies to a Claude Code started afterwards; one already running has to restart, which the menu offers, and it resumes the same session. It is a row in the workspace list: selecting a row shows its TUI, and the CLI keeps running while you are elsewhere. The six most recently used terminals stay open while out of view, so coming back to one shows it at once. Its title is a `/rename` in the TUI, then the title Claude Code gives the conversation (Codex gives none here), then the first message, and updates while the row is in view; renaming it in DSH stops that. Through a DSH restart, a page reload or a lost SSH connection the CLI keeps running on the remote machine, and so does its turn; selecting the row again shows the same process. After a restart of the remote machine, selecting it resumes the same session (`claude --resume` or `codex resume`). Archiving the row ends its CLI; undoing that and selecting it again resumes it. Select text and press Cmd+C to copy, as in any terminal; with local scrolling off, dragging over text in Claude Code copies it as you release the mouse, with no Cmd+C needed. Files dragged onto the window or pasted (Cmd+V, or Ctrl+V for an image) are uploaded to `.dsh-remote-agents/attachments/tui/` in the remote project and their paths go into the prompt; an image shows as `[Image #1]`. Each file can be up to 50 MB, folders are not supported, Git ignores that directory, and nothing cleans it up. The conversation lives only in the remote CLI, so DSH's history and search do not see it. Once started, the TUI manages its own model, and permissions follow the remote CLI's own settings. Codex runs without its full-screen mode, so the wheel scrolls through the conversation, and without its update prompt at launch, where the first Enter would install; run `codex update` on the remote machine to update it. An existing conversation cannot become a TUI one. The CLI's state shows in the sidebar like any conversation's: running while it works, waiting when it asks for a permission or a question, finished when it is done and you are not looking. It comes from the CLI's terminal title and screen, with no extra connection to the remote machine, and is known only while the terminal is open, so after restarting DSH a row shows it again once you open it. Its token usage goes to `dsh-usage-stats` like a chat's, one record per turn and model, read from the CLI's own log on the remote machine (Claude Code's session file and its subagents' files, or the Codex thread's file and those of its subagents, such as the reviewer of approval requests, which Codex runs in threads of their own): a few seconds after a turn ends while its terminal is open, and every 10 minutes for all TUI conversations, which also catches turns run while DSH was closed. Only the lines that hold usage are fetched, without the message text. The first read of a conversation also counts its earlier turns, at the times they ran. A subagent's usage counts toward the conversation's turn running at the time, under the subagent's own model. A turn stopped with Esc counts at once; a reply cut off that way is logged with only the usage it started with, so the output it had written so far is not counted. A turn that ends with no trace in the log, as when the CLI is killed, counts once its log has been quiet for 30 minutes.

## New workspaces from a project

**Add workspace › From a project** gives a project a second workspace on a branch of its own, so work there never touches the project's own folder, as Paseo's new worktree workspaces do. Choose a project — one entry per Git repository among your workspaces, on this computer or a saved machine — then either **New branch**, started from a branch you pick (the repository's default branch at first) and named by you or generated, such as `swift-otter`, or **Existing branch** to check out a local branch or one only on the remote, which then tracks it. **Create workspace** makes a Git worktree, adds it to DSH as `<project> · <branch>` right after the project, with the project's Workspace Tags, and opens it. A remote branch you start from is fetched first (up to 15 seconds; the copy already on the machine is used if that fails), and a new branch does not track the branch it started from. A workspace that is a folder inside its repository opens the same folder in the worktree.

- **Where worktrees go:** outside the repository, in `~/.dsh/worktrees/<repository>-<hash>/<branch>` on this computer and `~/.dsh-remote-agents/worktrees/<repository>-<hash>/<branch>` on a saved machine. Only worktrees under these folders are this plugin's to archive. Remote worktrees need Git and a POSIX shell on the machine, not Node.js.
- **Setup and teardown:** commit a `.dsh/worktree.json` to the repository to prepare a new worktree, for example to install dependencies or copy untracked files such as `.env`: `{ "setup": ["pnpm install", "cp \"$DSH_SOURCE_CHECKOUT_PATH/.env\" ."], "teardown": ["docker compose down"] }`. The worktree's own copy is used, or the project's when the branch has none. Commands run one after another at the top of the worktree, in the login environment of the machine, with `DSH_SOURCE_CHECKOUT_PATH` (the repository's main checkout), `DSH_WORKTREE_PATH` and `DSH_BRANCH_NAME`. The dialog lists the project's setup commands before you create and shows their output live; the window can be closed meanwhile. When the branch's commands differ from those listed, the workspace is still created but they do not run by themselves: they are listed in the log for you to choose **Run these commands**, **Skip the remaining setup** or **Delete this worktree**. The confirmation before archiving lists the teardown commands in the same way. If one fails or is stopped, the workspace is already in DSH: **Retry** runs it again, **Skip the remaining setup** finishes without the rest, and **Delete this worktree** removes the worktree, the branch it created and its DSH workspace. `paseo.json` is not read.
- **Archiving:** the project's worktrees are listed under the form, to open or archive. Archiving shows what would be lost first — changed or untracked files, commits on no remote — then archives the conversations of the worktree's workspace, stops remote CLI sessions working in it, runs the teardown commands, removes the worktree and removes its workspace from DSH. The branch is kept; **Also delete branch** is offered only when the branch is merged into the repository's default branch.

## For other plugins

The service `remoteAgentsWorktrees` (version 1) lets another DSH plugin work where the user's conversations do: list the Git projects among DSH's workspaces, inspect one, create a worktree workspace of it as the new-workspace dialog does, and run Git or shell commands in a workspace's folder on its machine, local or SSH. Only folders DSH lists as workspaces can be reached. `dsh-autofix` is built on it.

The service `remoteTerminals` (version 1) answers `isTui(sessionId)`: whether a DSH conversation's view is a CLI in a terminal. Remote Agents asks it, so that such a conversation's turns are left to that CLI.

## Install and upgrade

Install it from the plugin market beside Remote Agents and restart DSH. Nothing has to be set up.

- **Coming from Remote Agents 0.2.129 or earlier:** the TUI conversations are taken over on the first start, from Remote Agents' saved state, which is left as it was. Their terminals and CLIs on the remote machines keep running: the holder, the attachments folder and the worktrees stay under `~/.dsh-remote-agents/` on each machine.
- **What is saved where:** which conversations are TUI conversations, their details and the scrolling choice are in `~/.dsh/storages/dsh-remote-terminals/state.json`; the terminal launchers are in `terminal/` beside it. The render and scrolling choices of the browser stay under their earlier `remote-agents.*` keys, so they carry over.
- **The terminal launchers moved** with the plugin's folder. A shell DSH remembered from the earlier location is replaced the next time a remote conversation is in view.

## Development

```sh
pnpm --filter dsh-remote-terminals check
pnpm --filter dsh-remote-terminals pack:plugin
```

The tests run the terminal holder, the launcher, the TUI commands and worktrees on a real shell of this computer, and mount this plugin together with Remote Agents in one DSH context. They do not run a real DSH, a real SSH connection or a real Claude Code or Codex.
