# 自动修复

[English](README.md) | **简体中文**

在 DeepSeek Harness 里修复缺陷。无论缺陷来自哪个来源，每个缺陷都有自己的 Git worktree 和对话，按 计划 → 实现 → 审核（[模型分工](../model-flow/README.zh-CN.md)）运行，停在一次本地提交上。在你验收之前，不会推送任何东西，也不会告诉来源“已修复”。

> 尚未发布：这个包是私有的，插件市场会跳过它。

## 在对话里提交和验收

在项目的任意对话里输入 `/fix` 加问题描述，可以一起粘贴截图：

```
/fix 活动页在 iOS 上白屏
```

- 仓库按这条对话所在的工作区自动认出；不在仓库里时在开头加 `repo=<仓库名>`，要换分支加 `branch=<分支名>`，名字带空格时加引号。
- 缺陷在自己的 worktree 和自己的对话里修。这条对话里留下一张卡片显示进度，点“打开对话”过去。
- 修好后，任务对话里出现一张卡片：可以看模型的报告和改动，然后“通过验收”或“打回”。在任务对话里输入 `/fix <还有什么问题>`（可带截图）也是打回。
- 任务失败时同样会在任务对话里出一张卡片，可以“继续”。

看板仍然列出全部缺陷和任务，TAPD 等来源的缺陷从那里派发。

要做的功能走同一条路：`/flow wt=on <要做什么>`（需要[模型分工](../model-flow/README.zh-CN.md) 0.1.11 或更新版本）会在这里建一个任务，分支是 `feat/<编号>`，给模型的话按“任务”而不是“缺陷”来写，提交信息是 `feat: …`，模型和轮数用那条命令里选的。配合这个版本，任务的卡片就是流程自己的卡片：和 `/flow` 一样的进度，进度条末尾多出 **检查** 和 **验收**，报告下面是你能做的决定。在任务自己的对话里，最新一次流程的卡片带着任务，所以只有一张卡片而不是两张；更早的流程卡片留作那一轮的记录。

## 在另一台 DSH 上输入，由这台执行

平时在笔记本的 DSH 里工作、让一台一直开着的机器执行修复时：

- 在执行修复的那台 DSH 上添加仓库，并在 设置 → 自动修复 里打开“接收其他 DSH 转交的缺陷”。
- 笔记本的 DSH 只需要安装本插件，不用添加仓库，也不用填对方的地址或密码。
- 在笔记本上那个项目的对话里输入 `/fix`，缺陷会经由仓库所在的机器交给执行的那台；卡片留在这条对话里，进度、报告、改动、“通过验收”和“打回”都在卡片上。

两台 DSH 都能连上仓库所在的机器，交接就发生在那台机器上你自己账号的 `~/.dsh-autofix` 目录里。能登录那个账号的人也就能提交和验收缺陷，这和他们本来就能直接改仓库是同一个边界。两台 DSH 都需要 `dsh-remote-agents` 0.2.130 或更新版本和 `dsh-remote-terminals`；只有执行修复的那台需要 `dsh-model-flow`。

## 来源

自动修复本身不认识任何缺陷系统，缺陷通过**来源**进来：

- **手动录入**，内置：看板上的 **新建缺陷** 可以填标题、描述，并带最多 8 张图片（选择文件、从剪贴板粘贴，或拖到表单上）。
- **独立的来源插件**，负责对接缺陷系统或其他任何产生缺陷的地方：[dsh-tapd](../tapd/README.zh-CN.md) 是第一个。可以同时安装多个，它们的缺陷共用一个看板，各自保管自己的登录和设置。

缺陷的图片会作为附件发给每一步的模型，在描述里以 `[image N]` 标出。如果流程里有模型看不了图片，任务会只凭文字运行，并说明这一点。

## 功能

1. **拉取**：向每个来源要它当前待处理的缺陷；**新建缺陷** 可以手动加一个。来源也可以主动送来缺陷。
2. **指定**仓库和基线分支（多包仓库还可以选一个包）。和之前相似的缺陷（同一来源且标题前缀相同，如 `【活动页】`；或属于来源里的同一个项目）会自动带出同样的去处。
3. **开始**：在新分支 `<来源>/<缺陷>` 上建 worktree，在里面开一条对话，以缺陷内容为目标启动模型分工。
4. **检查**：审核通过后，先拦下敏感文件和密钥，再运行仓库的检查命令。检查失败会打回给模型。
5. **等你验收**：修复只在本地提交。看完报告和改动后，**通过验收**，或者**打回**并说明哪里要改：可以写字，可以附截图（选择、粘贴或拖入），也可以两者都有。
6. **通过验收**会合并到基线分支并推送（也可以按仓库设置为只推送修复分支），然后通知来源，由来源决定回写什么。
7. **删除工作区**：修复推出去之后，点了通过验收的那张卡片会问要不要删除这个工作区，你确认之前什么都不会删。确认后 worktree 被删除，对话被归档；分支已合并的话一并删除，只推送过的分支会保留。工作区里还有没提交的文件或没推送的提交时不会动它。已完成的任务上一直留着这个按钮，可以以后再删。

看板从对话顶部的 **缺陷** 按钮打开，也可以从 **设置 → 自动修复** 打开。

## 要求

- DSH 0.2.2-rc.1 或更新版本。
- `dsh-remote-agents` 0.2.130 或更新版本，以及 `dsh-remote-terminals`，用于在本机和已保存的 SSH 机器上建 worktree。
- 执行修复的那台 DSH 上需要 `dsh-model-flow` 0.1.7 或更新版本；从 0.1.8 起，模型直接在 **设置 → 自动修复** 里选。
- 仓库所在机器上的 Git 为 2.38 或更新版本（验收使用 `git merge-tree --write-tree`）。
- 至少一个来源插件。

上面的插件有哪个没在运行，设置页会在用到它的位置指出来，并给一个从你的插件市场安装它的按钮。

## 设置

**设置 → 自动修复** 里集中了一次修复依赖的全部设置，包括其他插件保管的那些：仓库、负责计划、实现和审核的模型（就是「模型分工」自己的那份选择，`/flow` 也用它）、任务怎么运行、缺陷从哪来。dsh-tapd 这样的来源插件把自己的设置放在这里的「缺陷来源」下，不再单独占一页。

仓库指的是一个代表该 Git 仓库的 DSH 工作区（“项目”），可以在本机，也可以在远程机器上。DSH 还没打开过的仓库，可以直接填它在运行 DSH 的那台机器上的文件夹路径，DSH 会把它打开成工作区。每个仓库可以设置：

- **提交前的检查**：每行一条命令。含 `{package}` 或 `{script}` 的命令会对修复涉及的每个包各运行一次；`{script}` 是该包在 **构建脚本** 里最先有的那个。
- **包目录**（`packages/*`）和 **共享路径**：用于多包仓库。属于哪个包由修复实际改动的文件决定，不靠缺陷内容去猜。修复涉及多个包时只给出提醒，不会拒绝。

## 安全规则

- 模型被告知不要提交、推送或写任何缺陷系统；提交、合并和推送都由插件完成。
- 改动 `.env*`、`.npmrc`、SSH 密钥或 `secret(s)` 路径，以及新增内容里疑似令牌、API key 或私钥的，一律不提交。
- 带 `security`、`payment`、`auth`、`migration`、`prod-incident` 标签的缺陷不会开始（列表可在设置里改）。
- 任务开始时，仓库自己的 worktree 初始化命令（`.dsh/worktree.json`）会直接运行，不再询问。

## 编写来源

来源是一个向 `autofix` 服务注册的 DSH 插件：

```ts
ctx.inject(['autofix'], scoped => {
  const remove = scoped.autofix.register({
    id: 'tracker',                 // 小写；会出现在每个缺陷的键、分支名和提交信息里
    name: 'Tracker',
    unready: () => signedIn ? undefined : { key: 'Sign in to Tracker first.' },
    fetch: async signal => [{ source: 'tracker', id: '42', ref: '42', title: '…', body: '纯文本', url: 'https://…', project: { id: 'web', name: 'Web' }, labels: [] }],
    report: async (item, event) => { /* event.kind: 'started' | 'review' | 'accepted' */ },
    image: async (item, index) => ({ data: bytes, mediaType: 'image/png' }),   // 缺陷声明了 images: n 时，取第 index 张
  });
  scoped.effect(() => remove);
});
```

- `fetch` 返回当前所有待处理的缺陷；它不再列出的缺陷会显示为“已不在待处理列表里”。不需要被动拉取的来源可以不写 `fetch`，有缺陷时调用 `autofix.submit(id, items)` 即可（告警、webhook、聊天消息等）。
- `report` 会在任务开始、修复等人验收（分支、提交、检查数）、验收通过（合并提交）时被调用，回写什么由来源自己决定。`accepted` 时它失败的话，任务会留着这次事件并提供 **重新回写**；Git 里已经完成的事不会撤销。
- `image` 交出缺陷的一张图片（缺陷用 `images` 说明有几张），在任务开始时被调用。`discard` 在缺陷修好或被删除时被调用。
- 送进来的缺陷会被校验；`id` 和 `title` 必填。

来源的设置应该放进「自动修复」的设置页。来源插件的客户端用客户端服务 `autofixSources`（版本 1）登记，这个服务在装有自动修复 0.1.2 或更新版本时存在：`register(id, { name, Panel, text? })` 返回一个取消登记的函数。`Panel` 是一个 React 组件，带着 `embedded` 属性画在该来源那一行下面；`text(key, values)` 用来翻译来源自己的提示，比如 `unready` 返回的那句。没有这个服务时，来源自己登记一个设置页。

## 还没做的

- 从另一台 DSH 管理派发池、预览、定时拉取。
- DSH 重启时正在运行的任务会被标为已停止；点 **继续** 会在原来的 worktree 里接着做。
